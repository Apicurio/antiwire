# antiwire status update, 2026-10-05

For context: antiwire is a pure-Java port of Square Wire (Square's protobuf library), with no Kotlin anywhere, built for Apicurio Registry first and Kafka later. The original is written in Kotlin and drags kotlin-stdlib, okio, and other heavy dependencies into every consumer.

## What exists on main today (110 commits)

**The library works and is complete.** Runtime, .proto parser, schema linker, loader (files, directories, zip/jar archives), command-line compiler, and the Java code generator. All of it on Java 11.

**The numbers that matter:**

- **Footprint.** The upstream runtime weighs 2.3 MB across 4 jars. Ours weighs 0.24 MB in 1 jar. That is 90 percent less. For the schema surface it is 94 percent less. Migrating Apicurio removes 10.5 MB of dependencies from the resolved graph, guava included.
- **Speed.** The operations Apicurio performs (parsing .proto files, linking them, converting them to descriptors) are 8 to 16 percent faster than upstream. Message encode/decode is at parity or better, after two fixes we found by measuring: a fast path in UTF-8 length computation that makes one workload 2.2x faster, and a zero-copy read for bytes fields that removed an extra full-payload copy.
- **Zero Kotlin dependencies** in production. This is the rule, and the build enforces it automatically on every run.

**The evidence.** We took Square Wire's own test suite, all of it: 967 cases, reconciled case by case against the exact source revision we ported (7.1.0). An automated check verifies at every build that no test was lost, no expected value was edited, and nothing was forgotten. On top of that: 122 interoperability tests against protoc (Google's official compiler), 24 security regression tests covering the library's historical CVEs, and the strongest proof: the code our generator produces is byte-for-byte identical to what the original compiler produces across 13 reference files.

**Apicurio.** On a local branch (never pushed, by design) the Apicurio files that used Wire have been migrated to our jars. All four affected modules pass their tests with the same counts as before the migration, and the descriptors they produce are byte-identical to the previous version's.

**Maintenance.** There is a documented procedure for tracking future Wire releases (with an automated watch that tells us when Square publishes a new tag), already rehearsed in a simulation against a real security advisory.

**Public API.** On maintainer request, no okio types appear in the public signatures: we own a `Bytes` type, and the old okio-typed forms remain as deprecated bridges so that code generated by the original compiler still compiles against us.

## What is still open

1. **The 0.1.0 release** ([issue #3](https://github.com/Apicurio/antiwire/issues/3)). Everything is ready: measurements signed off by the maintainer, a release build that produces jars plus checksums and manifests. What remains is the maintainer's final go, and the decision on who uploads the artifacts to the GitHub release. Currently deferred as not urgent.
2. **Kafka.** Deferred by the maintainer. When it resumes, proposal C1 (registry-free, Confluent-free protobuf client stack on vanilla kafka-clients) is written up and waiting in `docs/kafka-use-case-proposal.md`.
3. **One known bug** ([issue #2](https://github.com/Apicurio/antiwire/issues/2)). A proto that declares a message literally named `Bytes` produces generated code that does not compile, due to a name collision. Upstream shares the same class of problem with other names; it is documented, with two candidate fix directions written down. No urgency.
4. **The Apicurio PR.** The branch is ready locally; whether and when to open it is the maintainer's call.

In short: the technical work is done and verified. What remains are three maintainer decisions (publish, Kafka, PR) and one documented bug nobody is forced to rush on.
