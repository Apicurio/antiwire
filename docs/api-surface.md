# Runtime consumer API surface (phases 1 and 2 of the no-okio public API)

Design note for the standing D5a directive: the consumer-facing Java API of this port is
JDK-typed; okio remains legal internally as the engine layer. Phase 1 adds the wire-owned
bytes type and the JDK-typed canonical members next to the okio forms without removing or
changing any okio-typed behavior. Phase 2, chosen by the maintainer as option (a) below,
switches the port's generated code to those canonical forms; the pinned-upstream fixtures keep
compiling against the deprecated bridge. The contract is enforced mechanically by
`wire-runtime-java`'s `ConsumerApiSurfaceTest` (pattern: wire-schema-java's
`JdkSchemaLoaderValidationTest.noOkioTypesInPublicSignatures`).

## The fixture constraint that shapes everything

The wire-tests-java fixtures (99 classes) and wire-protoc-compat-java fixtures (49 classes)
are generated by the PINNED upstream compiler (DEC-5) and compile against this port's
runtime. The generated code references `okio.ByteString` directly: bytes fields hold it,
every message constructor calls `super(adapter, unknownFields)` with it, and builders feed it
to `addUnknownFields`. Removing or retyping any okio-typed signature those classes use breaks
their compilation, which is forbidden. Since phase 2 the port's own JavaGenerator emits the
`Bytes` forms, and the golden corpus is compared under the documented mapping below instead
of raw byte-identity; the fixtures are untouched because upstream's compiler never emits
`Bytes`.

## The dual-signature strategy

Each consumer-facing class keeps every okio-typed public member, unchanged in behavior, but
marked `@Deprecated` with javadoc pointing here and naming it the engine/compat layer; next
to it stands the JDK-typed canonical member. `@Deprecated` is documentation and a compiler
nudge only: nothing is removed and no behavior changes. Consumers who stay on the deprecated
forms keep compiling and running, exactly like the generated fixtures.

One source-compatibility caveat is inherent to adding same-named overloads: a null literal
at a call site that now has both a `ByteString` and a `Bytes` candidate
(`new AnyMessage(url, null)`, `copy(url, null)`, `addUnknownFields(null)`, and since phase 2
a hand-written `super(adapter, null)` in a Message subclass) becomes ambiguous
and needs a cast after recompilation, because neither type is more specific. Binary
compatibility is unaffected; no in-tree or fixture source passes null literals today. The
canonical `AnyMessage(String, Bytes)` constructor also fails fast on a null value where the
deprecated form deferred the failure to first use; its javadoc records this.

The consumer classes under the rule are `com.squareup.wire.ProtoAdapter`, `Message`
(including `Message.Builder`), and `AnyMessage`. The canonical surface after phase 1:

| Deprecated okio form | Canonical form |
|---|---|
| `ProtoAdapter.encodeByteString(E)` | `ProtoAdapter.encodeToBytes(E)` returning `Bytes` |
| `ProtoAdapter.decode(ByteString)` | `ProtoAdapter.decode(Bytes)` (plus the existing `decode(byte[])`, `decode(InputStream)`) |
| `ProtoAdapter.encode(BufferedSink, E)` | `encode(OutputStream, E)` (pre-existing) |
| `ProtoAdapter.decode(BufferedSource)` | `decode(InputStream)` (pre-existing) |
| `Message.unknownFields()` | `Message.unknownFieldsBytes()` |
| `Message.encodeByteString()` | `Message.encodeToBytes()` |
| `Message.encode(BufferedSink)` | `encode(OutputStream)` (pre-existing) |
| `Builder.addUnknownFields(ByteString)` | `Builder.addUnknownFields(Bytes)` |
| `Builder.buildUnknownFields()` | `Builder.buildUnknownFieldsBytes()` |
| `AnyMessage(String, ByteString)` ctor, `value` field, `copy(String, ByteString)` | `AnyMessage(String, Bytes)` ctor, `valueBytes()`, `copy(String, Bytes)` |
| `ProtoAdapter.BYTES`, `ProtoAdapter.BYTES_VALUE` constants | `ProtoAdapter.WIRE_BYTES`, `ProtoAdapter.WIRE_BYTES_VALUE` (phase 2) |

## The Bytes design

`com.squareup.wire.Bytes` is an immutable wrapper over a `byte[]` held privately: public
factories copy defensively (`of(byte[])`, `of(byte[], int, int)`, `encodeUtf8(String)`) and
`toByteArray()` copies out, so the payload is never externally mutable. `decodeHex` and
`decodeBase64` delegate to the vendored `okio.ByteString` internally (one conversion copy)
rather than re-implementing okio's decoders; `decodeBase64` keeps okio's null-for-invalid
contract. `toString` prints lowercase hex, truncated at 64 bytes with the total size, in the
spirit of okio's rendering. The public surface is intentionally minimal; the antiwire
consumer never needed md5, substrings, or comparisons.

The backing store is a plain `byte[]`, not a wrapped `okio.ByteString`, because the hot
paths are the two bridge directions below. Three package-private members carry the engine
traffic: `takeOwnership(byte[])` (adopt a freshly created array without copying),
`internalBytes()` (read-only access; same-package callers must not mutate), and the
`fromByteString`/`toByteString` converters (one copy each, unavoidable because the vendored
okio `ByteString` clones on both `of` and `toByteArray` across packages).

Copy costs on the canonical paths:

- `encodeToBytes` wraps the buffer's freshly-read array via `takeOwnership`; zero additional
  copies beyond the buffer read that `encode()`/`encodeByteString()` already paid.
- `decode(Bytes)` hands `internalBytes()` to the canonical `decode(byte[])` entry, which
  builds `ByteArrayProtoReader32` over it; the reader never writes its source array, so this
  is zero copies beyond what `decode(byte[])` already pays.
- `unknownFieldsBytes()` and `valueBytes()` copy out of the okio memo once per call
  (`fromByteString`); they do not memoize the `Bytes` form.
- `addUnknownFields(Bytes)` and the `AnyMessage(String, Bytes)` constructor pay one bridge
  copy (`toByteString`) so the append protocol and the okio field stay single-sourced in the
  deprecated members; these are builder/construction paths, not hot loops.

## What remains okio-typed and why

- `ProtoReader` and `ProtoWriter` (and `ReverseProtoWriter`): engine classes used
  pervasively by the engine itself. They are not consumer-facing in the way adapters and
  messages are; consumers reach streams through `encode(OutputStream)` and
  `decode(InputStream)`. Deliberately NOT deprecated. Since phase 2 they carry Bytes-typed
  members where generated code touches them: `ProtoWriter.writeBytes(Bytes)` and
  `ReverseProtoWriter.writeBytes(Bytes)` write the payload without copying, and
  `ProtoReader.endMessageAndGetUnknownFieldsBytes(long)` is the form generated decode feeds
  to `Builder.addUnknownFields(Bytes)` (the empty case returns the `Bytes.EMPTY` singleton).
- `ProtoReader32`, `ByteArrayProtoReader32`, `ProtoReader32AsProtoReader`: the reader
  surface `decode(ProtoReader)` exposes is engine; `readBytes()` still returns okio because
  the reader's internal buffer protocol is okio's. `WireBytesAdapter.decode` bridges through
  it with one copy.
- `FieldEncoding.rawProtoAdapter()`: for LENGTH_DELIMITED it now hands back
  `ProtoAdapter.WIRE_BYTES`, closing the phase-1 value-typed leak. Every internal consumer
  decodes and re-encodes unknown fields through the same adapter, so the raw unknown-field
  round-trip is value-type-consistent; the wire bytes are unchanged.
- `com.squareup.wire.internal.*` (bindings, `RuntimeMessageAdapter`, `Reflection`): the
  reflection machinery that constructs generated messages through their builders. Internal
  surface. It resolves whatever adapter string a `@WireField` names, so code generated in
  either era works: the fixtures' `#BYTES` strings resolve to the deprecated okio adapter,
  port-generated `#WIRE_BYTES` strings to the canonical one.
- `SchemaLoader`'s okio-typed constructor: the engine loading API; the okio-free consumer
  facade is `JdkSchemaLoader` (already recorded in docs/loading-api-inventory.md).
- `SchemaEncoder.encode(ProtoFile)` returning `okio.ByteString` and the schema adapter's
  `unknownFields(...)`: internal packages, engine use.
- Generated code from the pinned upstream compiler (the fixtures): bytes fields are
  `okio.ByteString`, compiled against the deprecated bridge. The port's own generator now
  emits `Bytes` everywhere it used to emit `ByteString` (phase 2 below).

Engine seams that intentionally call the deprecated okio forms carry
`@SuppressWarnings("deprecation")` with an "Engine layer" comment (FieldEncoding,
RuntimeMessageAdapter, Internal, Reflection, KotlinConstructorBuilder, AnyMessage's adapter
and packs, SchemaProtoAdapterFactory, SchemaEncoder). Uses inside a member that is itself
deprecated do not warn, which keeps the generated fixtures warning-tolerable; the default
compiler output stays at summary notes only.

## Enforcement

`ConsumerApiSurfaceTest` (wire-runtime-java) walks the consumer surface of the three
consumer classes plus their public nested classes and `FieldEncoding` (consumer-reachable
through `addUnknownField`) with reflection: public and protected constructors, methods, and
fields, implemented interfaces including their generic arguments, and generic type arguments
and array components throughout. It fails if any non-@Deprecated member names an `okio.*`
type. A second test pins the bridge as an exact set: the consumer-reachable members
exposing okio types must equal the documented member list, so a new okio-typed member fails
the suite even when deprecated, and removing a fixture-facing member is called out by name
rather than only through the fixture modules' compilation. The phase-2 constants sit inside
that contract by construction: `ProtoAdapter<Bytes>` carries no okio generics, and the
`Message(ProtoAdapter, Bytes)` constructor adds no okio signature, so the pinned 15-member
bridge is unchanged.

## The follow-up decision the maintainer owns

Phase 1 left generated code okio-typed. Closing that gap had exactly two shapes:

1. Switch the port's JavaGenerator to emit `Bytes` for bytes fields (and the `Bytes` forms
   of unknown fields and adapters). This breaks golden byte-identity, so the golden corpus
   and the pinned-upstream fixture strategy need re-baselining; the fixtures stay on the
   deprecated okio forms because they are generated by upstream's compiler, which never
   emits `Bytes`. A wire-owned `ProtoAdapter<Bytes>` constant and the
   `Message(ProtoAdapter, Bytes)` constructor story land here.
2. Keep okio.ByteString in generated code, documented as a permanent divergence shared with
   upstream-generated sources, and accept that consumers of generated types touch the
   deprecated layer for bytes fields.

The maintainer chose option (1) for phase 2; the section below is the record.

## Phase 2: the generator emits Bytes

Decision (maintainer, 2026-10-03): the port's JavaGenerator emits
`com.squareup.wire.Bytes` everywhere it emitted `okio.ByteString`: bytes field types
(scalar, repeated, map values), `google.protobuf.BytesValue` fields, the `unknownFields`
constructor parameter and its `Bytes.EMPTY` default, field default constants, builder
setters, and the adapters' unknown-field traffic. The wire format is untouched; the TYPE
changes, not the bytes on the wire.

### New runtime members that carry generated code

| Member | Role |
|---|---|
| `ProtoAdapter.WIRE_BYTES` (`ProtoAdapter<Bytes>`) | the canonical bytes adapter; wire-identical to deprecated `BYTES` |
| `ProtoAdapter.WIRE_BYTES_VALUE` (`ProtoAdapter<Bytes>`) | the canonical `google.protobuf.BytesValue` wrapper |
| `Message(ProtoAdapter, Bytes)` constructor | what generated `super(ADAPTER, unknownFields)` calls now |
| `ProtoWriter.writeBytes(Bytes)`, `ReverseProtoWriter.writeBytes(Bytes)` | zero-copy engine writes of unknown fields |
| `ProtoReader.endMessageAndGetUnknownFieldsBytes(long)` | the decode-side twin of `addUnknownFields(Bytes)` |

Naming rationale: the scalar slot `BYTES` and the wrapper slot `BYTES_VALUE` are permanently
occupied by the deprecated okio-typed constants the pinned fixtures reference, so the
canonical pair takes the `WIRE_` prefix (wire-owned value type). `ProtoAdapter.WIRE_BYTES`
reads as "the bytes adapter over wire's bytes type"; the alternative of renaming the
deprecated constants was rejected because those names are compiled into the fixtures.

### The mechanical mapping, checked against the golden corpus

The port's generated output diverges from upstream-generated output by exactly this mapping
(nothing else may differ; `wire-java-generator`'s `AllTypesGoldenBytesMappingTest` generates
the pinned wire-golden-files `all_types_proto3` corpus with the port CLI, rewrites the
UPSTREAM golden by the mapping, and requires the port's raw output to be byte-identical to
it, so any other divergence, including a regression back to an okio-typed member the mapping
covers, fails the suite):

| Upstream form | Port form |
|---|---|
| `okio.ByteString` (token, incl. the import) | `com.squareup.wire.Bytes` / `Bytes` |
| `unknownFields()` | `unknownFieldsBytes()` |
| `super.buildUnknownFields()` | `super.buildUnknownFieldsBytes()` |
| `reader.endMessageAndGetUnknownFields(` | `reader.endMessageAndGetUnknownFieldsBytes(` |
| `ProtoAdapter.BYTES` / `#BYTES` | `ProtoAdapter.WIRE_BYTES` / `#WIRE_BYTES` |
| `ProtoAdapter.BYTES_VALUE` / `#BYTES_VALUE` | `ProtoAdapter.WIRE_BYTES_VALUE` / `#WIRE_BYTES_VALUE` |

The import line moves to its new sorted position (the test sorts the golden's import
block; JavaPoet already emits the port's sorted), and `adapter` strings inside `@WireField`
follow the constant renames, which is what the reflection machinery (`ProtoAdapter.get`,
`FieldBinding`) resolves by name. The scalar constant-name choice has one source of truth,
`JvmLanguages.scalarAdapterConstantName`, which both the emitted adapter expressions and the
reflection adapter strings (`builtInAdapterString`, so map fields' key/value strings match)
derive from. `wire-java-generator`'s `GeneratedBytesCompileTest` proves the harder half
mechanically: it generates a model covering every bytes shape (scalar, repeated,
`BytesValue`, map value), compiles it with the JDK compiler against the port runtime, and
round-trips it byte-identically through both the generated adapter and the reflection
machinery, unknown fields included.

### What else moved with it

- The schema-driven surface follows: `SchemaProtoAdapterFactory` maps `bytes` and
  `google.protobuf.BytesValue` to the canonical adapters, so `Schema.protoAdapter` models
  bytes values as `Bytes` (known fields and unknown length-delimited values alike; the
  phase-1 `rawProtoAdapter()` leak closing is what made unknown values `Bytes`).
- The upstream-generated fixtures (wire-tests-java, wire-protoc-compat-java) are untouched:
  they still reference `ProtoAdapter.BYTES`/`BYTES_VALUE` and the okio constructor, all of
  which remain in the pinned 15-member bridge, and `RuntimeMessageAdapter` keeps the okio
  wrapper in its message-backed set next to the canonical one.
- No port-generated fixtures are committed in this repo (checked: the only generated trees
  in-tree are the two upstream-generated fixture modules), so nothing needed regeneration.

### Copy costs on generated-code paths

The `Bytes` bridges (`fromByteString`, `toByteString`) map the empty value to the singletons
in both directions, so the no-unknown-fields case never allocates. `Message` memoizes the
unknown fields in whichever form constructed it and derives the other lazily once (racy
derivation is benign, like `hashCode`): a generated `build()` hands the builder's `Bytes` to
the `Message(ProtoAdapter, Bytes)` constructor with no copy, `unknownFieldsBytes()` reads are
copy-free after the first, and the deprecated `unknownFields()` pays one bridge copy only when
it is called on a `Bytes`-constructed message. The dual memo retains the payload twice for a
message whose BOTH forms are read (a port-generated message that is hashed or compared and
also encoded through the reflection path); single-form readers retain one copy. `Builder.addUnknownFields(Bytes)` writes
through `ProtoWriter.writeBytes(Bytes)` with no copy, as does the reverse writer. Remaining
bridge costs, owned by the next perf session: `WireBytesAdapter.decode` and
`endMessageAndGetUnknownFieldsBytes` bridge through the okio reader forms (two copies per
value: the reader's own read plus the `fromByteString` conversion), where a reader that hands
out an adoptable `byte[]` would pay one.

### Known limitation: the `Bytes` import can be shadowed

A single-type-import shadows same-package types declared in other compilation units (JLS
6.4.1), so a proto declaring `message Bytes` in a package whose other messages also use bytes
fields generates output that cannot compile: sibling files bind bare `Bytes` to the runtime
type, and the message's own file collides with the import. Upstream shares this hazard class
for every name it imports (`okio.ByteString`, `java.time.Duration`, `kotlin.Unit`; a
same-package `message Duration` breaks upstream output identically); phase 2 only raises the
likelihood because `Bytes` is a plausible message name. The clean fix, per-file
always-qualified emission, needs javapoet `alwaysQualify`, which exists only in the palantir
fork that DEC-3 forbids; the gap is tracked as TASK-27.

### Performance note (out of scope here, recorded for the next session)

The /tmp/aw-perf harness is not in scope for phase 2 and was not re-measured. Its
`generate-models.sh` regenerates the workload models with the port CLI, so at the next perf
session the port-side models (all_types and bytes_heavy both carry bytes fields) come back
with `Bytes` fields, and the harness's `diff -rq gen/port gen/upstream` source-identity gate
must apply the same mapping above before comparing; `perf.IdentityCheck` compares wire bytes
and is unaffected by the value-type change.
