# antiwire compatibility matrix

Status: TASK-1 AC#2 deliverable, 2026-09-30. This matrix inventories the public surface the port must reproduce, the okio surface embedded in it, the parser and generator APIs, and the observed Apicurio call sites, and it names the owning task and migration requirement for every deliberate source change. It implements DEC-2 ([decisions.md](decisions.md)): functional and source compatibility for intended consumers, except at documented, individually justified migration sites; no precompiled ABI promise; upstream `.api` dumps serve as a boundary checklist, not a full-ABI gate. It does not reopen any settled decision. Every namespace, grouping, or mechanism item that awaits its owning task's evidence is marked PROVISIONAL in [section H](#h-provisional-items-awaiting-their-owning-tasks-evidence).

## B. Embedded okio types (namespace DECIDED: retained `okio.*` via vendored translation, OPEN-1 resolved by TASK-4)

The okio surface any I/O route must cover, re-verified at the pinned tag by an import scan of wire-runtime and wire-schema main sources:

- ByteString and companion operations: `okio.ByteString` (14 imports in wire-runtime main), `decodeBase64` (wire-runtime jvmMain `internal/JsonIntegration.kt`), `encodeUtf8` and `toByteString` (wire-schema `internal/SchemaEncoder.kt:39-40`), and `decodeHex` (wire-schema jvmMain `internal/fileSystems.kt:20`).
- Buffering and streams: `Buffer`, `BufferedSource`, `BufferedSink`, and the top-level `okio.source`, `okio.sink`, `okio.buffer` helpers (wire-runtime main).
- Exceptions and contracts: `okio.IOException`, `okio.EOFException`, `okio.Closeable`, `okio.utf8Size` (wire-runtime main; `okio.IOException` also in wire-schema main). These are JVM typealiases to `java.io.IOException`, `java.io.EOFException`, and `java.io.Closeable` in the pinned artifact (`okio/src/jvmMain/kotlin/okio/-JvmPlatform.kt:43-51`), so the JDK types satisfy them without translation; the same holds for `okio.ProtocolException` (`java.net.ProtocolException`), which appears at the tag only in test scope (wire-schema jvmTest `SchemaProtoAdapterTest.kt:30,174,196`) and stays reachable there.
- Filesystem surface: `okio.FileSystem` and `okio.Path` across wire-schema's public API (`SchemaLoader.kt:25` takes a `FileSystem` in its public constructor; `Root`, `WireRun`, `SchemaHandler`, `ClaimedPaths`, `CoreLoader`, `WireLogger`, the parser, and `Util` per research F3), `Path.Companion.toPath` (`Roots.kt:23`, `CoreLoader.kt:19`), `FileSystem.Companion.asOkioFileSystem` (jvmMain `SchemaLoader.kt:21`; the same file offers a secondary constructor over `okio.NioFileSystem` at line 28), `okio.openZip` (`Roots.kt:24`), and `okio.asResourceFileSystem` (`CoreLoader.kt:20`), all in jvmMain. `FileHandle` appears in the OPEN-1 inventory through the Apicurio call surface ([section F](#f-observed-apicurio-call-site-census)), not through any Wire main source at the tag; no wire-runtime or wire-schema main file imports it.
- In-memory sources: `Buffer`-backed sources; the loader's compression-relevant concern is ZIP, not gzip (research F3, B3 disposition in [plan-review.md](plan-review.md)).

The namespace decision is DECIDED (OPEN-1 resolution in [decisions.md](decisions.md), 2026-09-30): the port vendors a translated okio 3.18.2 subset as port source under the retained `okio.*` names in wire-runtime-java, with no production dependency on any okio or Kotlin artifact. The three consequence areas are recorded with the choice: (1) upstream test adaptation uses the static/property spellings ledgered in `okio-behavior-tests/ADAPTATION-LEDGER.md`; (2) generated code keeps referencing `okio.ByteString`, so no OPEN-4 namespace mapping is triggered for it; (3) the Apicurio loader sites swap coordinates and keep their `okio.*` imports, with FakeFileSystem patch-versus-vendor still the TASK-12/TASK-18 decision. Attribution obligations for the vendored okio code apply and are carried per file and in the NOTICE file (DEC-12). The retained `okio/` prefix stays in `config/retained-prefixes.txt`, and the negative control in [decisions.md](decisions.md) OPEN-1 demonstrates the duplicate-class check fails when a real okio jar joins a port-under-test classpath.

## C. Parser element model and ranges

Boundary evidence: `wire-schema/api/wire-schema.api` (77 public entries) plus source reads; the `internal` packages are excluded from the dump, so the parser boundary is established from `wire-schema/src/commonMain/kotlin/com/squareup/wire/schema/internal/parser/` (17 files) and the Apicurio census in [section F](#f-observed-apicurio-call-site-census).

- Element model: `ProtoParser`, `ProtoFileElement`, `MessageElement`, `EnumElement`, `EnumConstantElement`, `FieldElement`, `OneOfElement`, `ExtendElement`, `ExtensionsElement`, `GroupElement`, `OptionElement`, `OptionReader`, `ReservedElement`, `RpcElement`, `ServiceElement`, `SyntaxReader`, `TypeElement`. Kotlin `internal` is public in JVM bytecode and Apicurio consumes these types, so the port keeps them public and stable (DEC-2 scope; research F5).
- Range values: `ReservedElement.values` and `ExtensionsElement.values` are `List<Any>` holding `String` names, `Int` tags, or Kotlin `IntRange` tags (`ReservedElement.kt:25-38`, `ExtensionsElement.kt:26-39`); `toSchema()` renders `first`/`last`, substituting `max` once `last` reaches `MAX_TAG_VALUE`, which is `(1 shl 29) - 1` = 536,870,911 (`wire-schema/src/commonMain/kotlin/com/squareup/wire/schema/internal/Util.kt:82`; `ProtoParser.kt:500,545` map the `max` keyword).
- Entry points: `ProtoParser.Companion.parse(location, data)` (`ProtoParser.kt:676-678`), the `internal constructor` (`ProtoParser.kt:28`), and the public `readProtoFile()` (`ProtoParser.kt:53`). Apicurio exercises all three shapes today ([section F](#f-observed-apicurio-call-site-census)).
- Public Java range type: the documented public representation of reserved and extension ranges, with endpoint and maximum-value semantics tested and the consumer migration contract recorded, is owned by TASK-10; the migration itself is TASK-18. Wrong range types already fail loudly in `FileDescriptorUtils` (explicit `IllegalStateException` branches); the one silent path is `ProtobufFile.processMessageElement`'s final else-branch, covered by the delta-aware checks (research F5; TASK-18 AC#3 and AC#4).

## D. Profile and generator APIs

- `Profile` is an `expect class` (`Profile.kt:20` in commonMain) whose jvmMain actual exposes `javaTarget(type): TypeName?`, `kotlinTarget(type): KTypeName?`, and `getAdapter(type): AdapterConstant?` (`wire-schema/src/jvmMain/kotlin/com/squareup/wire/schema/Profile.kt:28-41`), importing `com.palantir.javapoet` and `com.squareup.kotlinpoet` types (`Profile.kt:18-21`). `AdapterConstant` likewise imports javapoet and kotlinpoet `ClassName` (`AdapterConstant.kt:18-19`). These poet references are why the upstream `wire-schema` POM carries mandatory poet `api` dependencies (research F2).
- Plan of record: Java-profile support (`Profile.javaTarget`, `getAdapter`, `AdapterConstant`, and the profile parsing stack `ProfileParser`, `ProfileFileElement`, `TypeConfigElement` in `internal`) moves to the optional Java-generator module, so no consumer of runtime or schema pulls generator dependencies (OPEN-2 fixed boundary; TASK-12 moves it, TASK-16 completes and verifies it). The optional generator may use a reviewed pure-Java JavaPoet; KotlinPoet appears nowhere in production artifacts (DEC-4).
- `Target` is an abstract class in wire-schema commonMain; the concrete `JavaTarget`, `KotlinTarget`, and `SwiftTarget` live in `wire-compiler/src/main/java/com/squareup/wire/schema/Target.kt:29,81,201`. The Kotlin and Swift generator products are excluded from the initial release (DEC-6), so `KotlinTarget`, `SwiftTarget`, and the `kotlinTarget()` KotlinPoet path are out of the production scope; `JavaTarget` and the CLI travel with the optional generator module owned by TASK-16.

## E. Generated-code contract

What generated Java code imports from the runtime, evidenced by the single upstream Java golden, `wire-golden-files/src/main/java/com/squareup/wire/proto3/java/all_types/AllTypes.java` (3,167 lines):

- Runtime types: `com.squareup.wire.{AnyMessage, EnumAdapter, FieldEncoding, Message, ProtoAdapter, ProtoReader, ProtoWriter, ReverseProtoWriter, Syntax, WireEnum, WireField}` (import lines 5-15).
- Internal helpers: `com.squareup.wire.internal.Internal` (line 16), a direct consequence of `@file:JvmName("Internal")` on `Internal.kt:16`. The generator emits calls to `Internal.countNonNull`, `Internal.immutableCopyOf`, `Internal.immutableCopyOfMapWithStructValues`, `Internal.immutableCopyOfStruct`, `Internal.sanitize`, `Internal.checkElementsNotNull`, and `Internal.missingRequiredFields` (`wire-java-generator/src/main/java/com/squareup/wire/java/JavaGenerator.java:1801,1835,1841,1847,2043,2183,2235`). Those names and that class name are therefore part of the compatibility contract, not an internal detail.
- External types crossing into generated output: `okio.ByteString` (line 34; used for bytes fields and `ByteString.EMPTY` defaults, lines 69, 180, 479) and `kotlin.Unit` (line 33; the well-known `Empty` type maps to `kotlin.Unit` fields, lines 247, 551, 767, 843).

Namespace-mapping consequences: the generated surface is where the OPEN-1 namespace choice meets OPEN-4 golden exactness. Upstream generated output is byte-identical to upstream goldens; the OPEN-1 choice has landed (2026-09-30) as retained `okio.*` names via vendored translation ([section B](#b-embedded-okio-types-namespace-decided-retained-okio-via-vendored-translation-open-1-resolved-by-task-4)), so no relocated `ByteString` mapping is triggered and the remaining bounded-mapping candidate is a replacement for the `kotlin.Unit` `Empty` representation, which DEC-4 bars from production artifacts since it would drag kotlin-stdlib into consumer compile classpaths. Any such mapping must be documented with rationale, reviewed, checked automatically against pinned upstream goldens, and its output must compile and run (OPEN-4, owner TASK-16, constrained by the landed OPEN-1 retained-okio-names decision). Evidence limits, from research F4: the Java golden corpus is exactly one file, upstream `wire-java-generator` has no standalone suite, and the compiler suite mixes Java-target cases with excluded features, so TASK-16 adds compensating Java-target cases beyond golden identity (plan-review F14, B5).

### Duplicate-class prevention rules (register row: coexistence excluded)

Deliberate coexistence of the port and an upstream Wire artifact on one application classpath is out of contract (DEC-2). These layout rules make accidental coexistence detectable rather than silent:

1. The port ships `com.squareup.wire.*` and any retained okio package names under its own Maven coordinates only, and never bundles upstream class files inside its own artifacts, so a duplicate class always means two distinct artifacts on the classpath, which resolution can list.
2. The shared verification entry point (TASK-2) resolves the full test and consumer classpath and fails when the same `com.squareup.wire` or retained okio class name arrives from two different artifacts, reporting both origins.
3. TASK-18 asserts the rule on the Apicurio integration classpaths (AC#5) and TASK-21 rechecks it on the release candidate (AC#4) and the published artifacts (AC#6); a duplicate-class finding is a release blocker, not a warning.
4. The optional generator artifact carries no runtime or schema classes of its own and depends on the core artifacts, so adding it cannot introduce a second copy (OPEN-2).
