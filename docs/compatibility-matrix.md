## B. Embedded okio types (namespace resolved 2026-10-01, OPEN-1)

The okio surface any I/O route must cover, re-verified at the pinned tag by an import scan of wire-runtime and wire-schema main sources:

- ByteString and companion operations: `okio.ByteString` (14 imports in wire-runtime main), `decodeBase64` (wire-runtime jvmMain `internal/JsonIntegration.kt`), `encodeUtf8` and `toByteString` (wire-schema `internal/SchemaEncoder.kt:39-40`), and `decodeHex` (wire-schema jvmMain `internal/fileSystems.kt:20`).
- Buffering and streams: `Buffer`, `BufferedSource`, `BufferedSink`, and the top-level `okio.source`, `okio.sink`, `okio.buffer` helpers (wire-runtime main).
- Exceptions and contracts: `okio.IOException`, `okio.EOFException`, `okio.Closeable`, `okio.utf8Size` (wire-runtime main; `okio.IOException` also in wire-schema main). `okio.ProtocolException` appears at the tag only in test scope (wire-schema jvmTest `SchemaProtoAdapterTest.kt:30,174,196`), where adapted tests catch it around adapter decode failures; an I/O route that relocates names still needs the type reachable in test scope.
- Filesystem surface: `okio.FileSystem` and `okio.Path` across wire-schema's public API (`SchemaLoader.kt:25` takes a `FileSystem` in its public constructor; `Root`, `WireRun`, `SchemaHandler`, `ClaimedPaths`, `CoreLoader`, `WireLogger`, the parser, and `Util` per research F3), `Path.Companion.toPath` (`Roots.kt:23`, `CoreLoader.kt:19`), `FileSystem.Companion.asOkioFileSystem` (jvmMain `SchemaLoader.kt:21`; the same file offers a secondary constructor over `okio.NioFileSystem` at line 28, upstream's own NIO bridge, relevant evidence for OPEN-1), `okio.openZip` (`Roots.kt:24`), and `okio.asResourceFileSystem` (`CoreLoader.kt:20`), all in jvmMain. `FileHandle` appears in the OPEN-1 inventory through the Apicurio call surface ([section F](#f-observed-apicurio-call-site-census)), not through any Wire main source at the tag; no wire-runtime or wire-schema main file imports it.
- In-memory sources: `Buffer`-backed sources; the loader's compression-relevant concern is ZIP, not gzip (research F3, B3 disposition in [plan-review.md](plan-review.md)).

Resolved 2026-10-01 (decisions.md OPEN-1): the okio 1.17.6 buffer subset is vendored under the original `okio.*` names in wire-runtime-java, together with original Path, FileSystem and FileMetadata types. Since DEC-14 (2026-10-06) okio is an engine detail: the consumer API is JDK-typed (`Bytes`, `JdkSchemaLoader`) and okio-typed members remain only as deprecated bridges and engine surfaces (see api-surface.md and loading-api-inventory.md). The list above is the historical inventory the route had to cover. Modern okio is Kotlin and barred from production scope (DEC-4); okio 1.x ended at 1.17.6 and is not assumed to be a drop-in replacement (source purity unverified, research F3). OPEN-1 requires that the choice record its consequences in exactly three areas, restated here as the standing requirement: (1) upstream test adaptation, since Wire's own tests bind `FakeFileSystem` and `"path".toPath()`; (2) generated code, whose output references `okio.ByteString` ([section E](#e-generated-code-contract)); (3) the Apicurio migration sites ([section F](#f-observed-apicurio-call-site-census)). Attribution obligations for any vendored okio code apply regardless of the namespace choice (DEC-12).

## D. Profile and generator APIs

- `Profile` is an `expect class` (`Profile.kt:20` in commonMain) whose jvmMain actual exposes `javaTarget(type): TypeName?`, `kotlinTarget(type): KTypeName?`, and `getAdapter(type): AdapterConstant?` (`wire-schema/src/jvmMain/kotlin/com/squareup/wire/schema/Profile.kt:28-41`), importing `com.palantir.javapoet` and `com.squareup.kotlinpoet` types (`Profile.kt:18-21`). `AdapterConstant` likewise imports javapoet and kotlinpoet `ClassName` (`AdapterConstant.kt:18-19`). These poet references are why the upstream `wire-schema` POM carries mandatory poet `api` dependencies (research F2).
- Plan of record: Java-profile support (`Profile.javaTarget`, `getAdapter`, `AdapterConstant`, and the profile parsing stack `ProfileParser`, `ProfileFileElement`, `TypeConfigElement` in `internal`) moves to the optional Java-generator module, so no consumer of runtime or schema pulls generator dependencies (OPEN-2 fixed boundary; TASK-12 moves it, TASK-16 completes and verifies it). The optional generator may use a reviewed pure-Java JavaPoet; KotlinPoet appears nowhere in production artifacts (DEC-4).
- `Target` is an abstract class in wire-schema commonMain; the concrete `JavaTarget`, `KotlinTarget`, `SwiftTarget`, `ProtoTarget`, and `CustomTarget` live in `wire-compiler/src/main/java/com/squareup/wire/schema/Target.kt:29,81,201,222,279`. The Kotlin and Swift generator products are excluded from the initial release (DEC-6), so `KotlinTarget`, `SwiftTarget`, and the `kotlinTarget()` KotlinPoet path are out of the production scope; `JavaTarget` and the CLI travel with the optional generator module owned by TASK-16. `ProtoTarget` (`.proto` emission) is retained in scope (DEC-6 scope note, 2026-10-06) and is ported into the generator module beside `JavaTarget` and `CustomTarget` (TASK-16.2); like upstream, it is reachable through the API only, since no CLI flag constructs it.

## E. Generated-code contract

What generated Java code imports from the runtime, evidenced by the single upstream Java golden, `wire-golden-files/src/main/java/com/squareup/wire/proto3/java/all_types/AllTypes.java` (3,167 lines):

- Runtime types: `com.squareup.wire.{AnyMessage, EnumAdapter, FieldEncoding, Message, ProtoAdapter, ProtoReader, ProtoWriter, ReverseProtoWriter, Syntax, WireEnum, WireField}` (import lines 5-15).
- Internal helpers: `com.squareup.wire.internal.Internal` (line 16), a direct consequence of `@file:JvmName("Internal")` on `Internal.kt:16`. The generator emits calls to `Internal.countNonNull`, `Internal.immutableCopyOf`, `Internal.immutableCopyOfMapWithStructValues`, `Internal.immutableCopyOfStruct`, `Internal.sanitize`, `Internal.checkElementsNotNull`, and `Internal.missingRequiredFields` (`wire-java-generator/src/main/java/com/squareup/wire/java/JavaGenerator.java:1801,1835,1841,1847,2043,2183,2235`). Those names and that class name are therefore part of the compatibility contract, not an internal detail.
- External types crossing into generated output: `okio.ByteString` (line 34; used for bytes fields and `ByteString.EMPTY` defaults, lines 69, 180, 479) and `kotlin.Unit` (line 33; the well-known `Empty` type maps to `kotlin.Unit` fields, lines 247, 551, 767, 843).

Namespace-mapping consequences: the generated surface is where the OPEN-1 namespace choice meets OPEN-4 golden exactness. Upstream generated output is byte-identical to upstream goldens; if the M0 namespace choice requires a bounded mechanical mapping in generated code (relocated `ByteString`, a replacement for the `kotlin.Unit` `Empty` representation, which DEC-4 bars from production artifacts since it would drag kotlin-stdlib into consumer compile classpaths), that mapping must be documented with rationale, reviewed, checked automatically against pinned upstream goldens, and its output must compile and run (OPEN-4, owner TASK-16, constrained by the OPEN-1 choice). Evidence limits, from research F4: the Java golden corpus is exactly one file, upstream `wire-java-generator` has no standalone suite, and the compiler suite mixes Java-target cases with excluded features, so TASK-16 adds compensating Java-target cases beyond golden identity (plan-review F14, B5).

Bytes mapping landed 2026-10-03, no-okio phase 2, extended 2026-10-06 by the Empty mapping (supersedes the TASK-16 byte-for-byte statement above as the standing golden contract): the ported generator emits `com.squareup.wire.Bytes` where upstream emits `okio.ByteString` (bytes fields, wrapper fields, unknown fields, defaults, adapter constants `ProtoAdapter.WIRE_BYTES`/`WIRE_BYTES_VALUE`), and `ProtoAdapter.UnitValue` with `ProtoAdapter.WIRE_EMPTY` where upstream emits `kotlin.Unit` with `ProtoAdapter.EMPTY` (TASK-16.1), so raw byte-identity with upstream goldens no longer holds; generated output diverges from upstream-generated output by exactly the documented mapping in docs/api-surface.md's phase-2 section, and that is checked mechanically (`wire-java-generator`'s `AllTypesGoldenBytesMappingTest` rewrites the upstream golden by the mapping and requires the port's raw `all_types_proto3` output to be byte-identical to it, so any other divergence, including a regression back to an okio- or kotlin-typed member, fails; `GeneratedBytesCompileTest` and `GeneratedEmptyCompileTest` additionally generate, JDK-compile at `--release 11`, and round-trip bytes- and Empty-covering models through both the generated adapter and the reflection machinery). The wire format is unchanged: only the Java value type differs. User-type name collisions (TASK-27, resolved 2026-10-06): the 2026-10-03 claim that a same-package `message Bytes` shadows the emitted import and breaks generated compilation was refuted by audit and pinned as regression coverage (`GeneratedBytesCollisionCompileTest`); the generator omits contested imports and fully qualifies runtime references, so the verified shapes (same-package and cross-package message Bytes, a Bytes message with its own bytes field, repeated bytes, map values, repeated messages, an enum named Bytes, nested Bytes, proto2, oneof, extension fields, and messages colliding with always-emitted imports FieldEncoding/ProtoWriter/Internal) generate, compile at `--release 11`, and bind every field to its intended type. Collision shapes outside that list are unverified, not proven safe; the earlier "same inherited hazard as upstream" sentence was unverified and is withdrawn (docs/api-surface.md records the mechanism).

Empty gap recorded 2026-10-02, TASK-16 batch B, resolved 2026-10-06 by TASK-16.1: generated code for any proto using `google.protobuf.Empty` used to declare `kotlin.Unit` fields (upstream mapping, required for golden identity) and call `ProtoAdapter.EMPTY`, while the port runtime's constant is `ProtoAdapter<Void>` (`wire-runtime-java/.../ProtoAdapter.java:452` vs upstream jvmMain `ProtoAdapter.kt:319` `ProtoAdapter<Unit>`), so such output compiled against the port runtime neither without kotlin-stdlib (`package kotlin does not exist`) nor with it (`Unit cannot be converted to Void`); the delivery audit at 295ef5f replayed both failures. The resolution is the generator-remaps half of the OPEN-4 choice, not a runtime retyping: `JavaGenerator` maps `ProtoType.EMPTY` to `ProtoAdapter.UnitValue`, emits `ProtoAdapter.WIRE_EMPTY`, and the `@WireField` adapter string follows (`JvmLanguages.builtInAdapterString`, `#WIRE_EMPTY`); the deprecated Void-typed `EMPTY` is untouched. `java.time.{Duration,Instant}` and struct types compile and run against the port as-is (verified by the person.proto CLI smoke: generate, javac, encode/decode round-trip, and since phase 2 mechanically by `GeneratedBytesCompileTest`). The dynamic-model half was already resolved by TASK-26 (`Schema.protoAdapter` maps `google.protobuf.Empty` to `ProtoAdapter.WIRE_EMPTY` over the `UnitValue` singleton); the generated-code half is now the bounded golden-checked mapping above, proven by `GeneratedEmptyCompileTest` (CLI-generate, `javac --release 11` with no Kotlin jar on the classpath, adapter plus reflection round-trips, present-versus-absent and duplicate singular occurrences) and by the revived `wire-protoc-compat` `EmptyRoundTripTest.allEmpty`, which generates `AllEmpty` with the port generator at test time and byte-compares against the protoc oracle (`AllEmptyOuterClass`, now generated by `scripts/generate-protoc-compat-fixtures.sh`; the fixture script's wire-compiler side still excludes the proto because the pinned upstream generator would emit `kotlin.Unit`).

### Duplicate-class prevention rules (register row: coexistence excluded)

Deliberate coexistence of the port and an upstream Wire artifact on one application classpath is out of contract (DEC-2). These layout rules make accidental coexistence detectable rather than silent:

1. The port ships `com.squareup.wire.*` and any retained okio package names under its own Maven coordinates only, and never bundles upstream class files inside its own artifacts, so a duplicate class always means two distinct artifacts on the classpath, which resolution can list.
2. The shared verification entry point (TASK-2) resolves the full test and consumer classpath and fails when the same `com.squareup.wire` or retained okio class name arrives from two different artifacts, reporting both origins.
3. TASK-18 asserts the rule on the Apicurio integration classpaths (AC#5) and TASK-21 rechecks it on the release candidate (AC#4) and the published artifacts (AC#6); a duplicate-class finding is a release blocker, not a warning.
4. The optional generator artifact carries no runtime or schema classes of its own and depends on the core artifacts, so adding it cannot introduce a second copy (OPEN-2).
