# Architecture decisions (M0)

Status: adopted for execution; each entry lists its rationale from the research report
(docs/research-wire-java-port-2026-09-29.md) and is open to revision from second opinions.

## D1. Keep the `com.squareup.wire.*` Java packages

The port keeps upstream package and type names exactly. Reasons: upstream test sources run
unmodified against our artifacts (the top-level project requirement is to pass the same test
suite); code generated by Wire 6/7 stays binary-compatible with the ported runtime; the Apicurio
swap becomes a dependency-coordinate change only. We do not republish under Square's Maven
groupId (see D2), and the README and NOTICE state clearly that this is a community port.

## D2. Publish under `io.apicurio` groupId, not `com.squareup.wire`

Artifact names: `wire-runtime-java`, `wire-schema-java` (parent `io.apicurio:antiwire`).
Java packages stay `com.squareup.wire.*` per D1; only the Maven coordinates differ. This keeps
Maven Central free of any confusion with Square's published artifacts while remaining an honest
derivative work with attribution.

## D3. Java 11 bytecode, built on JDK 17

`maven.compiler.release=11`, CI builds on Temurin 17. Reason: Kafka client modules require Java
11 (`minClientJavaVersion = 11` in apache/kafka trunk); Apicurio requires more, so 11 is the
intersection. Consequence: no `sealed`, records, `var`, or text blocks in main sources
(recorded in the translation conventions, docs/translation-conventions.md).

## D4. Maven build, Kotlin only in the test scope

Reason: Apicurio consumes Maven artifacts; a pure-Java Maven build needs no Kotlin plugin for
main sources, which structurally prevents Kotlin from leaking into shipped artifacts. Kotlin
appears only where we compile upstream test sources verbatim.

## D5. Vendor the okio subset inside `wire-runtime-java`, package `okio`, pure Java

Evidence from the M0 inventory (wire 7.1.0 sources):

- Main code uses: `ByteString`, `Buffer`, `BufferedSource`, `BufferedSink`, `Path`,
  `FileSystem`, `IOException`, `EOFException`, `Closeable`, plus the extension-style calls
  (`toPath`, `toByteString`, `encodeUtf8`, `decodeHex`, `decodeBase64`, `source`, `sink`,
  `buffer`, `openZip`, `asOkioFileSystem`, `asResourceFileSystem`).
- `wire-schema` main references `FileSystem`/`Path` in 10 files; `SchemaLoader` exposes them in
  its public API. Therefore the vendored subset must include a `FileSystem`/`Path` layer
  implemented over `java.nio.file` and the JDK zip filesystem, not just buffers.
- Tests additionally use: `okio.fakefilesystem.FakeFileSystem`, `okio.ProtocolException`.

Decisions:
1. Vendor in the `okio` package name (not an internal package). Reason: upstream test sources
   import `okio.*`; same-package vendoring lets them compile untouched, and avoids a find and
   replace across every translated file. The NOTICE documents the origin (Apache 2.0, Square).
2. Base the buffer layer (ByteString, Buffer, Segment, BufferedSource/Sink,
   RealBufferedSource/Sink, Utf8, Base64) on okio 1.17 Java sources where the okio 3 surface
   matches, adapting to the okio 3 member set where wire code or tests call newer members.
   okio 3.18 Kotlin sources are the semantic reference for every adapted member.
3. Implement `Path`, `FileSystem` (metadata reads, list, source/sink, atomicMove, delete),
   `openZip`, `asOkioFileSystem`, and a minimal `FakeFileSystem` in Java over
   `java.nio.file`/zipfs. Target: only the members wire and its tests use, plus okio's own unit
   tests for the vendored classes (ported as our tests).
4. Kotlin extension compatibility for verbatim tests: a test-scoped Kotlin artifact
   (`antiwire-test-extensions`) re-declares the okio 3 extension names (`encodeUtf8`,
   `decodeHex`, `toPath`, `.buffer()`, `.source()`, and the rest from the inventory) as
   extensions over the vendored Java classes. Main artifacts stay Kotlin-free.

Rejected alternative: depend on `okio-jvm`. It is Kotlin-compiled and drags kotlin-stdlib,
which defeats the port's purpose.

## D6. kotlinpoet/javapoet out of the core artifacts

`wire-schema-java` ships without poet dependencies; `AdapterConstant`/`Profile` poet references
and the code generators move to a separate generator artifact (M3) which may depend on
palantir javapoet (pure Java). Reason: zero non-JDK dependencies is the footprint requirement,
and Apicurio consumes none of the codegen surface.

## D7. gson-support deferred

Apicurio does not use `wire-gson-support` (its Maven tree references only `wire-schema`).
Defer until a consumer asks; tracked outside the initial backlog scope.

## D8. Upstream pin

The port tracks square/wire tag 7.1.0 until M5 defines the re-sync procedure. Apicurio will be
validated against this port directly rather than backporting to wire 6.4.0 semantics (the 6.4
to 7.0 delta is small per the upstream changelog).
